Machine Learning · Finance & Risk

Loan Default Predictor

Modelado de credit risk con el dataset Home Credit: desde business understanding y Exploratory Data Analysis hasta XGBoost, SHAP explanations y deployment en Streamlit.

Proyecto educativo

Pregunta del proyecto

¿Podemos estimar la probabilidad de que un solicitante de préstamo incurra en default? Este proyecto construye un end-to-end Machine Learning pipeline que toma información del solicitante y predice credit risk de una manera didáctica y amigable para estudiantes.

Idea principal: el output no es simplemente “aprobar” o “rechazar”. El output más informativo es una default probability. Esa probabilidad puede convertirse posteriormente en una lending decision mediante un threshold elegido por la institución.

Por qué este proyecto importa

Credit risk modeling es una de las aplicaciones clásicas de Data Science en Finance. Bancos y lenders deben decidir qué solicitantes probablemente pagarán sus obligaciones y cuáles presentan mayor probabilidad de default. Si una institución aprueba demasiados préstamos riesgosos, aumentan las pérdidas. Si rechaza demasiados buenos borrowers, pierde ingresos y aleja buenos clientes.

Intuición económica: un solo default grande puede eliminar las ganancias obtenidas de muchos préstamos buenos. Por eso classification, probability estimation e interpretability son tan importantes en credit scoring.

Dataset y prediction target

El proyecto utiliza el dataset Home Credit Default Risk. El principal training file contiene 307,511 applicants y 122 variables. La variable objetivo se llama TARGET:

Valor Significado
0 El applicant pagó el préstamo; no hubo default dentro del horizonte definido.
1 El applicant incurrió en default. En este dataset, la etiqueta corresponde a payment difficulties que señalan credit distress relevante.

Las features incluyen income, credit amount, annuity, age, employment time, family information, housing variables y external credit-related scores como EXT_SOURCE_1, EXT_SOURCE_2 y EXT_SOURCE_3.

Una visión de Machine Learning del problema

Supongamos que cada applicant está representado por un vector de features:

x = (x₁, x₂, …, xₚ) donde cada xj representa una característica observada, como income, annuity, age o un external score.

La tarea consiste en aprender una función que transforme estos inputs en una probability of default:

p̂(x) = P(Y = 1 | X = x) Interpretación: dadas las características x del applicant, ¿cuál es la probabilidad estimada de que pertenezca a la clase default?

Después de estimar esa probabilidad, puede aplicarse una decision rule:

ŷ = 1 si p̂(x) ≥ t;    ŷ = 0 si p̂(x) < t Aquí t es el classification threshold. Un lender más conservador puede usar un threshold menor para marcar a más applicants como riesgosos.

El learning roadmap de cinco etapas

1. Setup & Data
2. EDA
3. Preprocessing
4. Models & Evaluation
5. SHAP & Export

El proyecto está estructurado como una secuencia de aprendizaje paso a paso. Los notebooks avanzan desde comprender los raw data, hacia cleaning y feature engineering, luego training y model evaluation, y finalmente exportan los artifacts necesarios para deployment en una Streamlit app.

Stage 1 — Setup & Data

Cargar el dataset, inspeccionar dimensiones, comprender el target y establecer el train/test workflow. Esta etapa responde una pregunta fundamental: ¿qué estamos prediciendo exactamente y por qué?

Stage 2 — Exploratory Data Analysis (EDA)

Estudiar la distribución del target y de las predictor variables. Aquí comenzamos a preguntar si income, annuity, age o external scores parecen estar relacionados con default risk.

Stage 3 — Preprocessing & Feature Engineering

Tratar missing values, codificar categorical features, escalar numerical variables y crear engineered ratios como credit-to-income y annuity-to-income.

Stage 4 — Models & Evaluation

Entrenar tres models —Logistic Regression, Random Forest y XGBoost— y compararlos utilizando metrics apropiadas para un imbalanced credit-risk problem.

Stage 5 — SHAP & Export

Explicar predictions utilizando SHAP y exportar los model artifacts para que el final pipeline pueda utilizarse dentro de la Streamlit application.

Por qué Class Imbalance importa

Solo alrededor de 8.1% de los loans son defaults, mientras aproximadamente 91.9% son non-defaults. Esto se conoce como class imbalance.

Advertencia importante: si un model predice “no default” para cada applicant, todavía tendría aproximadamente 91.9% Accuracy. Ese número suena alto, pero el model fallaría completamente en el business objective, porque no identificaría ningún risky borrower.

Por eso este proyecto no depende solamente de Accuracy. También utiliza SMOTE, class-aware metrics y probability-based evaluation.

Accuracy = (TP + TN) / (TP + TN + FP + FN) Accuracy es fácil de calcular, pero puede ser engañosa cuando una clase domina.
Recall = TP / (TP + FN) Recall es especialmente importante en credit risk porque un False Negative implica aprobar a un applicant que posteriormente incurre en default.

SMOTE y resampling

SMOTE significa Synthetic Minority Oversampling Technique. En lugar de simplemente duplicar default cases, crea synthetic minority examples mediante interpolación entre observaciones existentes de la minority class.

Pequeño ejemplo: si un defaulting borrower tiene income = 30k y otro tiene income = 35k, SMOTE puede crear un synthetic borrower con income alrededor de 32k o 33k, junto con valores interpolados correspondientes para otras features. Esto ayuda al model a “ver” con mayor claridad la default region durante training.

Los tres models del proyecto

1) Logistic Regression

Este es el baseline classification model. Calcula un linear score y lo transforma mediante una sigmoid function:

z = β₀ + β₁x₁ + β₂x₂ + ··· + βₚxₚ p̂(x) = 1 / (1 + e−z) La sigmoid function convierte cualquier real-valued score en un número entre 0 y 1, que interpretamos como default probability.

Por qué es útil: es simple, rápida e interpretable. Si funciona bien, proporciona un benchmark sólido.

2) Random Forest

Random Forest combina muchos Decision Trees. Cada tree observa un bootstrap sample de los datos y un random subset de features. La final probability se obtiene del ensemble de trees.

p̂(x) = (1/B) Σb=1B Tb(x) Aquí Tb(x) es la prediction del tree b, y B es el número de trees.

Por qué ayuda: captura nonlinear patterns e interactions que Logistic Regression puede no representar adecuadamente.

3) XGBoost

XGBoost es el model más fuerte del proyecto. Construye trees secuencialmente, donde cada nuevo tree intenta corregir los errores del ensemble anterior.

FM(x) = Σm=1M γmhm(x) En palabras: el final score es la suma de múltiples weighted weak learners. Esta boosting strategy suele funcionar muy bien con structured tabular data.

En la documentación del proyecto, el XGBoost model obtuvo un AUC de aproximadamente 0.76, un resultado sólido para un problema real difícil.

Evaluation Metrics e interpretación

Debido a que esta es una credit-risk classification task, utilizamos múltiples metrics en lugar de un único número.

Precision

Precision = TP / (TP + FP)

De los applicants que el model predijo que harían default, ¿cuántos realmente hicieron default?

Recall

Recall = TP / (TP + FN)

De todos los true defaulters, ¿cuántos identificó correctamente el model?

F1 Score

F1 = 2 × (Precision × Recall) / (Precision + Recall)

Equilibra Precision y Recall en una sola summary measure.

AUC-ROC

AUC = P(s(X+) > s(X−))

Interpretación: si seleccionamos aleatoriamente un defaulting borrower y un non-defaulting borrower, ¿con qué frecuencia el model asigna el score más alto al defaulter?

Interpretación de negocio: un False Negative suele ser uno de los errores más costosos en lending, porque significa que el banco aprobó un risky borrower. Por eso Recall y AUC son especialmente importantes.

Worked probability example

Supongamos que el model evalúa un borrower y devuelve:

p̂(x) = 0.29

Esto significa que la estimated default probability es 29%. Si el lender utiliza threshold t = 0.50, el applicant no sería marcado automáticamente como default. Pero si el lender utiliza un threshold más conservador t = 0.25, el mismo applicant sería marcado como risky.

Lección: el model output y la business decision están relacionados, pero no son idénticos. El threshold representa el risk appetite de la institución.

Preprocessing, Scaling y Feature Engineering

El proyecto aplica standard supervised-learning hygiene:

  • Train/test split con stratification para mantener proporciones de clase similares en ambos sets.
  • One-hot encoding para categorical variables.
  • StandardScaler para numerical variables cuando corresponde.
  • Engineered features como CREDIT_INCOME_RATIO = AMT_CREDIT / AMT_INCOME_TOTAL y ANNUITY_INCOME_RATIO = AMT_ANNUITY / AMT_INCOME_TOTAL.
z = (x − μ) / σ Esta es la standardization formula. Centra una numerical variable restando su mean y la reescala dividiendo entre su standard deviation.
Advertencia sobre data leakage: el scaler debe hacer fit únicamente sobre el training set. Si se utiliza información del test set durante preprocessing, la evaluación se vuelve demasiado optimista.

Model Explainability con SHAP

Las regulated financial applications necesitan más que predictive performance. También necesitan explicaciones. Este proyecto utiliza SHAP (SHapley Additive exPlanations) para explicar tanto global predictions como individual predictions.

f(x) = φ₀ + Σj=1p φj La baseline prediction es φ₀. Cada feature contribution φj empuja la final prediction hacia arriba o hacia abajo.

Por ejemplo, un external score bajo puede elevar el risk, mientras que un stable income o una menor annuity burden puede reducirlo.

Por qué un estudiante debería prestar atención: SHAP es un puente entre predictive accuracy e interpretability. Ayuda a responder la pregunta: “¿Por qué el model produjo esta prediction?”

Deployment: del Notebook a una Web Application

El proyecto no se limita a notebooks. También incluye una Streamlit application que carga el final model, scaler y feature names, acepta user input y devuelve una predicted default probability junto con una risk category.

Risk categories utilizadas en la app: prob < 0.20 → LOW 0.20 ≤ prob < 0.50 → MEDIUM prob ≥ 0.50 → HIGH

Este es un elemento importante de portfolio porque demuestra no solamente model training, sino también packaging y comunicación de resultados a un end user.
