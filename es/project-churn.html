Bank Customer Churn Prediction

Un caso end-to-end de Machine Learning que evalúa si los atributos de los clientes pueden utilizarse para identificar un mayor riesgo de churn manteniendo un workflow riguroso de train/test.

Completado

1. Pregunta del proyecto

¿Pueden los atributos de un cliente utilizarse para estimar el riesgo de que abandone el banco, y qué decisiones de modelado producen predicciones útiles para clientes que el modelo nunca ha visto?

En este proyecto, churn significa que un cliente abandona el banco o deja de utilizar sus servicios. La variable objetivo es binaria: Exited = 1 para un cliente que hizo churn y Exited = 0 para un cliente que permaneció. El repository contiene 10,000 registros de clientes y 18 columnas originales, seguidas por data cleaning, feature engineering, model comparison y un reusable prediction module.

Idea clave: churn prediction es un problema de supervised binary classification. Conocemos el resultado histórico de cada cliente del training set y usamos esos ejemplos etiquetados para aprender una regla capaz de estimar churn risk en clientes futuros.

2. ¿Qué está aprendiendo un classification model?

Sea Y el resultado del cliente:

Y ∈ {0,1}
Y = 1 significa churn; Y = 0 significa que el cliente permaneció.

Sea X el conjunto de características disponibles del cliente, como age, credit score, tenure, balance, number of products, activity status y geography. Un classifier intenta aprender una relación entre X y Y.

Muchos classifiers pueden interpretarse como modelos que estiman una probabilidad:

p(X) = P(Y = 1 | X)
Se lee como: “la probabilidad de que el cliente haga churn, dadas las características observadas del cliente”.

Luego, un decision threshold puede convertir esa probabilidad en una predicción de clase. Por ejemplo, con threshold = 0.50:

ŷ = 1 si p(X) ≥ 0.50; de lo contrario ŷ = 0

El threshold no tiene que ser 0.50. En un retention program real, un banco podría reducirlo o aumentarlo dependiendo del costo de no detectar a un cliente con alta probabilidad de churn frente al costo de contactar innecesariamente a un cliente leal.

3. Dataset y predictive features

El proyecto comienza con atributos como CreditScore, Geography, Gender, Age, Tenure, Balance, NumOfProducts, HasCrCard, IsActiveMember, EstimatedSalary, Satisfaction Score, Card Type y Point Earned. Algunos identifier fields se eliminan porque no representan información predictiva significativa.

Feature type Ejemplos Por qué importa
Continuous / numeric Age, Balance, CreditScore, EstimatedSalary Pueden capturar relaciones graduales con churn risk.
Count / discrete Tenure, NumOfProducts, Point Earned Pueden representar customer history, engagement y relaciones con productos.
Binary HasCrCard, IsActiveMember Ya poseen una interpretación significativa 0/1.
Categorical Geography, Gender, Card Type Deben codificarse numéricamente antes de que muchos algoritmos puedan utilizarlas.

4. Data leakage: un modelo puede ser “demasiado bueno” por la razón equivocada

Uno de los hallazgos más importantes del proyecto es que la variable Complain está casi perfectamente alineada con el target. En el análisis del repository presenta aproximadamente 0.99 de Pearson correlation con Exited y es casi idéntica row-by-row. Esto la convierte en un ejemplo clásico de target leakage.

Por qué data leakage es peligroso: si una variable contiene información que solamente estaría disponible después —o como parte— del evento de churn, el modelo puede parecer extremadamente preciso durante el desarrollo y aun así fallar en producción. Un predictive model debe utilizar únicamente información realmente disponible en el momento en que se realiza la predicción.

Esta es una lección académica importante: high accuracy no es automáticamente evidencia de un buen modelo. Primero debemos preguntar si la información utilizada para obtener esa accuracy es legítima.

5. Preprocessing: colocando las variables en una escala utilizable

Las variables numéricas continuas pueden vivir en escalas muy diferentes. Por ejemplo, Age puede medirse en decenas, mientras que Balance puede estar en miles. Standardization transforma una variable numérica en unidades de standard deviations respecto de su media:

z = (x − μ) / σ
x = valor original, μ = feature mean, σ = feature standard deviation.
Mini ejemplo. Supongamos que la mean age es μ = 50 años y la standard deviation es σ = 10 años. Un cliente de 65 años tiene:

z = (65 − 50) / 10 = 1.5

Ese cliente está 1.5 standard deviations por encima de la edad promedio.

El proyecto deja intencionalmente indicadores binarios como HasCrCard e IsActiveMember como valores 0/1. Las categorical variables se transforman mediante one-hot encoding, creando indicator columns que los algoritmos pueden utilizar sin imponer un orden numérico artificial.

6. Class imbalance: por qué Accuracy puede engañar

Los datos originales contienen aproximadamente 80% non-churners y 20% churners. Esto importa porque un classifier ingenuo podría predecir “stay” para todos y obtener cerca de 80% Accuracy identificando cero clientes que realmente hacen churn.

Idea clave: cuando existe class imbalance, la calidad del modelo debe evaluarse con métricas como Precision, Recall, F1 Score y ROC-AUC, no solamente Accuracy.

7. Train/test split y por qué SMOTE pertenece solamente al training set

El proyecto utiliza un stratified 80/20 train/test split: aproximadamente 8,000 clientes para model development y 2,000 clientes untouched para evaluación. El test set permanece real y desbalanceado para que se comporte como la población que el modelo encontraría en la práctica.

SMOTE significa Synthetic Minority Over-sampling Technique. Crea observaciones sintéticas de la minority class interpolando entre observaciones vecinas de esa clase.

xnew = xi + λ(xneighbor − xi)
donde 0 ≤ λ ≤ 1. El nuevo punto queda ubicado entre dos observaciones de la minority class.

SMOTE se aplica solamente después del train/test split y únicamente al training data. Aplicarlo antes del split permitiría que información sintética derivada de observaciones que terminarían en el test set se filtre hacia model development.

8. Seis classification models

El proyecto compara seis algoritmos. Cada uno representa una forma diferente de aproximar la decision boundary desconocida entre churners y non-churners.

Model Core idea Interpretación didáctica
Logistic Regression Models log-odds as a linear function of predictors. Baseline simple e interpretable para probabilistic classification.
Decision Tree Recursively splits the feature space. Crea reglas human-readable del tipo “if/then”.
Random Forest Averages many decision trees trained on randomized samples/features. Reduce la inestabilidad de un solo árbol y captura patrones no lineales.
Support Vector Classifier Finds a separating boundary with maximum margin. Se concentra en observaciones cercanas a la decision boundary.
Gradient Boosting Builds weak learners sequentially to correct prior errors. Cada nuevo árbol se concentra en errores cometidos por el ensemble anterior.
K-Nearest Neighbors Classifies using nearby observations in feature space. “Clientes similares a este tendieron a hacer churn o a permanecer.”

9. Logistic Regression: el probability baseline

Logistic Regression es especialmente útil para comprender classification porque convierte un linear score en una probabilidad utilizando la logistic —o sigmoid— function.

p(X) = 1 / [1 + e−(β₀ + β₁X₁ + ··· + βₚXₚ)]

La expresión dentro del exponential es un linear predictor. La sigmoid comprime cualquier valor real al intervalo entre 0 y 1.

El mismo modelo puede escribirse mediante log-odds:

log[p/(1−p)] = β₀ + β₁X₁ + ··· + βₚXₚ

Para un aumento de una unidad en Xj, manteniendo fijas las otras variables, eβⱼ representa el cambio multiplicativo en los odds. Esta es una de las razones por las que Logistic Regression continúa siendo importante incluso cuando un modelo más flexible termina mostrando mejor performance.

10. Decision Trees y Random Forest

Un Decision Tree realiza preguntas repetidas como “¿Age > 52?” o “¿IsActiveMember = 0?” y divide el dataset en grupos progresivamente más homogéneos.

Una medida común de impurity es Gini impurity:

Gini = 1 − Σ pk2
Para binary classification: Gini = 1 − p02 − p12.
Mini ejemplo. Si un node contiene 80% stayers y 20% churners:

Gini = 1 − 0.8² − 0.2² = 1 − 0.64 − 0.04 = 0.32.

Un node perfectamente puro tiene Gini = 0.

Random Forest construye muchos árboles en lugar de confiar en uno solo. Para classification, cada árbol vota por una clase o aporta una probability, y el forest agrega esos resultados:

p̂forest(X) = (1/B) Σ p̂b(X)
B es el número de árboles. El averaging ayuda a reducir variance y mejorar robustness.

En este proyecto, Random Forest es seleccionado porque ofrece el mejor balance general en F1 Score y ROC-AUC, además de permitir feature-importance analysis.

11. Confusion Matrix: comprendiendo los errores de predicción

Todo binary classifier produce cuatro resultados básicos:

Realmente hizo churn Realmente permaneció
Predicted churn True Positive (TP) False Positive (FP)
Predicted stay False Negative (FN) True Negative (TN)

Accuracy

(TP + TN) / N

Fracción de todas las predicciones que fueron correctas.

Precision

TP / (TP + FP)

Entre los clientes que el modelo predijo que harían churn, ¿cuántos realmente hicieron churn?

Recall

TP / (TP + FN)

Entre los clientes que realmente hicieron churn, ¿cuántos identificó el modelo?

F1 Score

2 × Precision × Recall / (Precision + Recall)

Harmonic mean que equilibra Precision y Recall.

Mini ejemplo. Supongamos que un test set contiene:

TP = 120, FP = 40, FN = 80.

Precision = 120/(120+40) = 0.75
Recall = 120/(120+80) = 0.60
F1 = 2(0.75×0.60)/(0.75+0.60) ≈ 0.67.

Este ejemplo muestra por qué una sola métrica rara vez cuenta toda la historia.

12. ROC Curve y AUC

La Receiver Operating Characteristic (ROC) curve evalúa el classifier a través de muchos probability thresholds. Representa:

True Positive Rate = TP/(TP+FN) False Positive Rate = FP/(FP+TN)

El Area Under the ROC Curve (AUC) resume la capacidad de discrimination. Una interpretación útil es:

AUC = P(scorechurner > scorenon-churner)

Así, un AUC de 0.80 puede interpretarse de la siguiente manera: si seleccionamos aleatoriamente un churner y un non-churner, el modelo asignará el score de riesgo más alto al churner aproximadamente 80% de las veces.

Importante: AUC mide ranking discrimination. No garantiza que las predicted probabilities estén bien calibrated. Un modelo puede ordenar correctamente a los clientes y aun así sobreestimar o subestimar la verdadera probabilidad de churn.

13. Por qué model evaluation debe utilizar unseen data

Un modelo puede memorizar patrones de su training sample. Por eso, evaluar performance sobre los mismos clientes utilizados para fit del modelo produce una estimación optimistamente sesgada de generalization performance.

El proyecto mantiene un untouched test set durante model selection. Solo después de seleccionar el modelo, el Random Forest final se vuelve a entrenar utilizando todos los registros reales de clientes. El final production fit no utiliza SMOTE, de modo que sus probability estimates permanezcan alineadas con la distribución real de clases en lugar de un mundo artificial 50/50.

14. Interpretando Feature Importance con cuidado

Random Forest feature importance ayuda a identificar qué variables contribuyen con mayor fuerza a las decisiones predictivas del forest. En el proyecto, algunos predictors importantes incluyen: Age, NumOfProducts, IsActiveMember, Balance y Geography.

Feature Importance no implica causalidad. Si Age recibe alta importance, significa que el modelo encontró Age útil para prediction en este dataset. No demuestra que cambiar Age cause churn, ni explica por sí sola el mecanismo subyacente.

16. ¿Qué enseña este proyecto?

  • Predictive performance comienza con data quality. Data leakage puede invalidar incluso un modelo técnicamente sofisticado.
  • Class imbalance cambia la forma en que debemos interpretar las métricas.
  • Resampling debe mantenerse completamente separado del test set.
  • Diferentes algoritmos incorporan diferentes supuestos sobre la decision boundary.
  • F1 y ROC-AUC complementan Accuracy cuando la minority class es importante.
  • Prediction no es causation. Una variable puede ser útil para prediction sin ser un causal driver.
  • Deployment requiere reproducible preprocessing. Las mismas transformaciones utilizadas durante training deben aplicarse a clientes futuros.
