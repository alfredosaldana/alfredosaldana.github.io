1. Por qué el mejor Training Score no significa el mejor modelo

Una empresa de telecomunicaciones quiere identificar clientes que podrían cancelar su servicio (churn) el próximo mes. Un modelo entrenado con clientes históricos produce una predicción para cada cliente nuevo. Pero ¿en qué modelo confiar: Logistic Regression, Decision Tree, Random Forest o k-Nearest Neighbors (k-NN)? Incluso después de elegir el algoritmo, debemos configurar sus opciones. Son dos preguntas relacionadas, pero diferentes: Model Selection elige estrategias de modelado; Hyperparameter Tuning elige configuraciones dentro de una estrategia.

El desempeño en Training muestra qué tan bien se ajusta un modelo a los datos usados para aprender. No nos dice de forma confiable cómo funcionará con futuros clientes. El procedimiento tentador —probar muchos modelos y publicar el mejor número obtenido en Test— contamina la evaluación. En su lugar seguiremos una secuencia defendible: reservar Test, definir la métrica, comparar alternativas mediante folds de Training/Validation, volver a ajustar la mejor opción sobre los datos de desarrollo y consultar Test una sola vez al final.

El primer ejemplo será suficientemente pequeño para calcular a mano. El segundo será un experimento reproducible en Python con 360 clientes sintéticos y más Features. Ambos responden a la misma pregunta empresarial, pero el segundo añade preprocessing realista. Los resultados son educativos; no son pronósticos del desempeño de empresas reales.

Un resultado alto no demuestra que la selección haya sido correcta. También debemos preguntar: **¿qué información pudo utilizar cada procedimiento y en qué momento?**

2. Objetivos, conocimientos previos y qué demostraremos

Al finalizar, podrás distinguir un Parameter de un Hyperparameter; construir tres folds de Cross-Validation; calcular su Accuracy; realizar un Grid Search completo; compararlo con Randomized Search; identificar el optimismo de selección; explicar Nested Cross-Validation; y auditar un Pipeline para detectar Leakage. También deberás justificar por qué se reserva Test incluso si el modelo seleccionado obtiene allí un resultado decepcionante.

Solo necesitas promedios, fracciones y comprender que un clasificador supervisado relaciona Features con un Target categórico. Introduciremos Balanced Accuracy, regularization strength, stratification, refitting y selection bias antes de utilizarlos formalmente. Si has estudiado las Guías 5, 6, 12, 15 y 21, reconocerás ideas previas, pero este capítulo presenta las definiciones necesarias para estudiarlo de manera independiente.

La ruta intelectual será: un dataset pequeño → predicciones dentro de cada fold → búsqueda completa → sesgo e incertidumbre → Nested CV → comparación reproducible de algoritmos → Test intacto. Estimar el desempeño de todo el proceso de selección es más difícil que medir un modelo ya especificado. Nested CV existe precisamente para separar esas preguntas.

Llamaremos development set al conjunto disponible para ajustar modelos y seleccionar configuraciones. Contiene observaciones que se usarán como Training y como Validation interna. El Test set permanecerá fuera de todas las decisiones. Cuando entrenemos el modelo final con todas las observaciones de desarrollo, ya no habrá folds retenidos internamente, pero Test seguirá intacto.

4. Parameters versus Hyperparameters: ¿quién aprende qué?

Un Parameter es una cantidad estimada utilizando Training. Logistic Regression aprende intercepto y pendientes; Decision Tree aprende umbrales de división; k-NN conserva los casos etiquetados de Training. Un Hyperparameter es una opción fijada externamente que controla cómo ocurre ese aprendizaje. Ejemplos son el número de vecinos \(k\), max_depth de un árbol, la intensidad inversa de Regularization \(C\) de Logistic Regression y el número de folds.

En k-NN, dada una nueva caída de uso \(x_*\), calculamos las distancias a los clientes de Training, \(d_i=|x_i-x_*|\); ordenamos las distancias; y votamos usando las \(k\) etiquetas más cercanas. Las observaciones y etiquetas provienen de Training; \(k\) se define desde fuera del ajuste. En Logistic Regression, el coeficiente \(\beta_1\) se aprende, mientras que \(C\) controla la Regularization impuesta durante ese aprendizaje.

Modelo Aprendido con Training Elegido mediante tuning
k-NN Registros etiquetados n_neighbors, weights
Logistic Regression Intercepto, coeficientes C, tipo de penalización
Decision Tree Divisiones y predicciones de hojas max_depth, min_samples_leaf
Random Forest Árboles y estimaciones de hojas n_estimators, max_depth

No todas las configuraciones necesitan optimizarse. Primero debemos elegir rangos plausibles según los datos y los recursos disponibles. La Random Seed normalmente es un control de reproducibilidad, no un Hyperparameter empresarial para seleccionar porque una semilla afortunada produzca mayor puntuación.

5. Elegir la métrica antes de observar los resultados

Supongamos que la empresa desea detectar clientes próximos a cancelar, pero cada llamada de retención tiene un costo. Accuracy es la proporción de clasificaciones correctas. Recall mide las cancelaciones detectadas entre todas las cancelaciones reales. Precision mide las cancelaciones reales entre los clientes señalados. Balanced Accuracy promedia el Recall de Churn y la Specificity de los clientes que permanecen.

\[\operatorname{Accuracy}=\frac{TP+TN}{TP+TN+FP+FN}\]
\[\operatorname{BalancedAccuracy}=\frac12\left(\frac{TP}{TP+FN}+\frac{TN}{TN+FP}\right)\]

TP es un cliente que cancelará y fue señalado, FN es una cancelación no detectada, FP es un cliente estable señalado incorrectamente y TN es un cliente estable identificado correctamente. Si 90 de 100 permanecen, predecir siempre Stay produce 90% Accuracy, pero Recall de Churn = 0 y Balanced Accuracy = \((0+1)/2=0.50\). Una cifra alta de Accuracy puede ocultar la incapacidad de detectar cancelaciones poco frecuentes.

En nuestro ejemplo manual de 15 clientes usaremos Accuracy para facilitar las votaciones; en el conjunto más grande y desbalanceado utilizaremos Balanced Accuracy, definida de antemano. Esta diferencia responde al objetivo de cada experimento educativo, no a una selección oportunista de la métrica. Antes de desplegar un modelo también necesitaríamos evaluar costos, Calibration de probabilidades y capacidad de intervención. La métrica principal y el criterio para resolver empates deben fijarse antes de la búsqueda.

6. Three-fold Cross-Validation: las particiones exactas

Una sola división Training/Validation puede hacer que un candidato parezca demasiado bueno o demasiado malo por azar. K-Fold Cross-Validation (CV) repite la evaluación reteniendo subconjuntos diferentes. Aquí K = 3; no confundas esa K mayúscula (cantidad de folds) con \(k\) minúscula (cantidad de vecinos de k-NN).

Ronda CV IDs usados como Validation IDs usados como Training Tamaño
1 1, 4, 7, 10, 13 Todos los demás 10 Training + 5 Validation
2 2, 5, 8, 11, 14 Todos los demás 10 Training + 5 Validation
3 3, 6, 9, 12, 15 Todos los demás 10 Training + 5 Validation

Durante la ronda 1 se ajusta un modelo k-NN nuevo utilizando solamente los diez clientes que no pertenecen al Fold 1. Predecimos los cinco clientes retenidos y contamos los errores. Descartamos ese ajuste. La ronda 2 construye un modelo nuevo con otros diez clientes; los registros que antes fueron Validation pueden ser Training en otra ronda, pero nunca dentro de la misma ronda en que se evalúan. Repetimos para Fold 3. Así, cada cliente se evalúa una vez con un modelo que no utilizó su etiqueta al entrenarse.

Como los folds tienen el mismo tamaño, la Accuracy media de los tres folds coincide con dividir el número total de predicciones correctas fuera de muestra entre 15. Si los tamaños fuesen distintos, ambos resultados podrían diferir: la media da el mismo peso a cada fold y la Accuracy agrupada da el mismo peso a cada observación. Debemos indicar qué cálculo estamos haciendo.

Con \(k=1\), la etiqueta vecina más cercana es 0: el modelo predice 0 y no detecta esta cancelación. Con \(k=3\), las etiquetas son 0, 0 y 1; sigue prediciendo 0. Para \(k=1\), en Fold 1 acertamos tres de cinco: Accuracy \(=3/5=0.60\); en Fold 2 también \(3/5=0.60\); en Fold 3, \(2/5=0.40\). Así:

Estas cifras provienen de observaciones retenidas dentro de development, no de Test. Una cifra de \(0.80\) sobre un solo fold pequeño sería evidencia muy limitada. Encontrarla en tres folds ayuda, aunque con solo 15 observaciones permanece una incertidumbre considerable.

9. Grid Search: todos los candidatos, no solo el ganador

Grid Search evalúa todas las combinaciones de una grilla discreta definida previamente. Elegimos cinco cantidades de vecinos, \(k\in\{1,3,5,7,9\}\), y dos reglas: uniform (cada vecino recibe un voto) y distance (los vecinos más cercanos reciben mayor peso). El producto cartesiano contiene \(5\times2=10\) configuraciones. Con tres folds se realizan 30 ajustes independientes. Esto es importante porque el costo crece aproximadamente con el número de candidatos multiplicado por el de folds.

k Accuracy uniforme Accuracy ponderada por distancia
1 53.33% 53.33%
3 66.67% 66.67%
5 66.67% 66.67%
7 80.00% 66.67%
9 66.67% 66.67%

El ganador según la Accuracy CV promedio definida previamente es k=7 con votación uniforme. ¿Por qué ponderar por distancia no mejora necesariamente las predicciones? Porque aumenta la influencia de observaciones muy próximas, incluso cuando su etiqueta contiene ruido; cercanía no garantiza verdad. Un \(k\) mayor suaviza ciertas irregularidades, pero también puede mezclar grupos de clientes realmente diferentes. No afirmamos que \(k=7\) sea óptimo para cualquier problema: solo gana entre estos diez candidatos, usando estos folds y esta métrica.

El search space necesita más que nombres: debemos definir rangos, métrica, diseño de CV, presupuesto computacional y regla para empates. Sin documentar esas decisiones, el proceso será difícil de auditar o reproducir.

10. Qué significa la variación entre folds y qué no significa

Incluso con el mismo candidato, el desempeño observado cambia cuando se retienen clientes diferentes. Por ejemplo, los scores de \(k=3\) son 0.80, 0.60 y 0.60; su media es 0.6667. La Standard Deviation muestral entre folds se calcula como:

\[s=\sqrt{\frac{(0.80-0.6667)^2+2(0.60-0.6667)^2}{3-1}}\approx0.1155\]

La dispersión es de 11.55 puntos porcentuales. Para \(k=7\), los tres scores son 0.80 y su desviación empírica entre folds es cero. ¡Eso no significa que exista incertidumbre cero acerca de clientes futuros! Los folds son pequeños, comparten gran parte de Training y proceden de la misma muestra. Los scores son estadísticamente dependientes y calcular mecánicamente \(s/\sqrt3\) no produce necesariamente un intervalo válido para el modelo desplegado.

Podemos inspeccionar distribuciones de scores, utilizar divisiones repetidas o agrupadas según corresponda y estimar intervalos sobre muestras independientes suficientemente grandes. Nunca debemos convertir la desviación de CV en una garantía precisa para producción. Tampoco conviene elegir un candidato porque su media superó a otra por una diferencia pequeña e inestable; importan la complejidad, las restricciones operativas y las reglas de desempate definidas previamente.

La variabilidad observada es una propiedad de esta evaluación. **Una dispersión pequeña entre folds no demuestra generalización robusta.**

12. Selection Bias y el sesgo del ganador

Imagina 20 configuraciones candidatas que en realidad tienen el mismo desempeño verdadero de 0.65. Sus puntuaciones observadas en Validation fluctúan porque las muestras son finitas. Supongamos, solo para una demostración numérica, que cada score observado se comporta como \(0.65+\varepsilon\), con ruido Normal independiente de media cero y Standard Deviation de 0.06. Cada score individual es insesgado: su esperanza es 0.65. Pero al elegir el máximo de 20 candidatos, seleccionamos la realización de ruido más favorable.

\[\widehat j=\operatorname*{arg\,max}_{1\le j\le20}\widehat S_j\]
\[E[\max_j\widehat S_j]>0.65\]

La desigualdad ilustra el optimismo de selección bajo esta simulación. No significa que la verdadera calidad del modelo ganador haya aumentado. Podemos reproducir el fenómeno generando 20 scores ruidosos por experimento simulado y guardando el mayor. El gráfico siguiente utiliza una semilla fija y 2,500 experimentos; no representa mediciones de nuestros clientes de telecomunicaciones.

La idea se relaciona con las comparaciones múltiples: cuantas más configuraciones, transformaciones y Thresholds probamos sobre el mismo resultado de Validation, mayor es la posibilidad de encontrar una cifra espectacular por suerte. Un error habitual consiste en presentar el mejor score CV como una estimación insesgada del procedimiento completo de búsqueda. En general sirve para ordenar candidatos, no para auditar de forma independiente el proceso entero. Por eso necesitamos un Outer Holdout o Nested CV.

No eliminamos el sesgo de selección por utilizar un buscador más sofisticado si seguimos seleccionando y evaluando con la misma información. La protección es separar los roles de los datos.

13. La trampa del preprocessing: fit debe ocurrir dentro de cada fold

Supongamos que faltan algunas mediciones de caída de uso e imputamos con la mediana. Supongamos además que estandarizamos una variable antes de aplicar Logistic Regression o k-NN. Ambas operaciones aprenden cantidades: mediana, media y Standard Deviation de Training. Si calculamos esos valores utilizando todo development antes de CV, cada fold de Validation influye en las transformaciones que supuestamente debe evaluar, aun si no usamos sus etiquetas Churn.

Para contrastar numéricamente, imaginemos un fold de Training con caídas 10, 20 y 30, mientras Validation contiene 100. La Standardization correcta aprende media \(\mu=20\) y desviación estándar poblacional:

\[\sigma=\sqrt{\frac{(10-20)^2+(20-20)^2+(30-20)^2}{3}}\approx8.165\]
\[z_{Validation}=\frac{100-20}{8.165}\approx9.798\]

Si mezclamos indebidamente 10, 20, 30 y 100 para ajustar el preprocessing, la media se vuelve \(40\), la desviación \(\sqrt{1250}\approx35.355\), y ese mismo dato de Validation se transforma en \((100-40)/35.355\approx1.697\). El cliente no ha cambiado; hemos contaminado la distribución de referencia del preprocessing.

Procedimiento correcto dentro de cada fold: imputer.fit(X_fold_train), scaler.fit(imputed_fold_train) y model.fit(transformed_fold_train,y_fold_train); después predict en Validation reutilizando las transformaciones ajustadas sin recalcular sus parámetros. Un Pipeline automatiza esta secuencia al pasarlo directamente a una búsqueda CV. El refit final vuelve a aprender las transformaciones con todo development, nunca con Test.

La pregunta analítica es qué clasificador ajustado equilibra mejor la detección de Churn y la identificación correcta de clientes estables. 15. Diseño del Pipeline: transformaciones sin acceso a Validation

Para columnas numéricas aplicamos SimpleImputer(strategy='median') y después StandardScaler(). Para categorías utilizamos OneHotEncoder(handle_unknown='ignore'). Un ColumnTransformer une ambas ramas, y un Pipeline coloca el clasificador después de ese transformador. En cada fold de CV, GridSearchCV.fit clona el Pipeline completo y ajusta todos sus pasos usando solo las filas de Training interno.

Etapa ¿Aprende con Training del fold? ¿Qué hace con Validation?
Numeric median imputation Sí: mediana para cada Feature Reutiliza las medianas almacenadas
StandardScaler Sí: medias y escalas Reutiliza la configuración
OneHotEncoder Sí: categorías observadas Reutiliza las mismas columnas
Logistic Regression Sí: coeficientes e intercepto Predice sin reajustarse

El encoder categórico maneja categorías nuevas sin modificar el número de columnas de salida. Es distinto de generar variables Dummy independientemente en Training y Validation; hacerlo por separado puede cambiar las dimensiones y el significado de las Features.

Una transformación congelada no significa que no podamos procesar nuevos clientes. Significa que transform sobre Validation, Test o producción no utiliza esos registros para recalcular parámetros estadísticos. En nuestro segundo ejemplo existen valores faltantes a propósito, así que esta diferencia tiene consecuencias prácticas. Incluiremos el código fuente completo y pasaremos el Pipeline entero al buscador de Cross-Validation, no una matriz previamente transformada con todos los datos.

16. Four-fold GridSearchCV: todos los resultados de C

Logistic Regression estima coeficientes minimizando una Log Loss penalizada. En scikit-learn, \(C>0\) representa la intensidad inversa de Regularization: un \(C\) menor significa mayor penalización; uno mayor, menor penalización. Los coeficientes son Parameters aprendidos; \(C\) es un Hyperparameter. Fijamos \(C\in\{0.1,1,10\}\) y utilizamos cuatro folds stratified sobre los 288 clientes de development.

C Fold 1 Fold 2 Fold 3 Fold 4 Balanced Accuracy media
0.1 0.5243 0.5695 0.5338 0.6053 0.5582
1 0.6822 0.6221 0.5844 0.6316 0.6301
10 0.6822 0.6390 0.5750 0.6485 0.6362

La media para \(C=10\) se calcula como:

\[\overline B_{C=10}=\frac{0.6822+0.6390+0.5750+0.6485}{4}\approx0.6362\]

Cada número procede de ajustar un Pipeline nuevo con los registros de Training de ese fold y predecir exclusivamente su Validation. Con tres candidatos y cuatro folds, realizamos \(3\times4=12\) ajustes, más un refit final sobre todo development si refit=True.

La mejor media es apenas mayor con \(C=10\) que con \(C=1\): aproximadamente 0.0061, es decir, 0.61 puntos porcentuales. Esto no constituye evidencia convincente de una ventaja universal. Reportamos el ganador según el criterio predefinido sin afirmar que esa diferencia pruebe superioridad estadística. Test continúa intacto.

17. Comparar algoritmos justamente: Logistic Regression versus Random Forest

Model Selection significa comparar familias de modelos ajustados, no solo números dentro de una familia. También optimizamos Random Forest con 150 árboles y seis combinaciones: max_depth en {3, 7, None} y min_samples_leaf en {2, 8}. Usamos los mismos cuatro folds CV y la misma Balanced Accuracy que en Logistic Regression. No permitimos que Random Forest use otro Test ni una regla de puntuación más favorable.

Familia candidata Búsqueda Mejor Balanced Accuracy CV de desarrollo
Logistic Regression C = 0.1, 1, 10 0.6362 (C = 10)
Random Forest 3 profundidades × 2 tamaños mínimos de hoja 0.6051 (profundidad = 7, hoja = 2)

Una regla de selección definida previamente es escoger la familia con mejor Balanced Accuracy media, evaluada sobre folds equivalentes. Aquí gana Logistic Regression. Podríamos incorporar complejidad, tiempo de predicción o un Recall mínimo, pero esos criterios deben quedar establecidos antes de abrir Test. Un Threshold elegido para maximizar beneficios operativos también exigiría un modelo explícito de costos y selección mediante development.

Este ejemplo no demuestra que Logistic Regression sea siempre superior a Random Forest. Exploramos grillas finitas y pequeñas, sobre datos sintéticos generados con un mecanismo Logistic, lo que favorece naturalmente cierta estructura lineal. La conclusión solo se refiere al protocolo definido. Un presupuesto de búsqueda mayor o un proceso generador diferente podrían cambiar la comparación.

18. Randomized Search: probabilidad de explorar una región favorable

Randomized Search extrae una cantidad fija de configuraciones desde distribuciones previamente definidas, en lugar de evaluar todo el producto cartesiano. Esto puede ahorrar tiempo cuando el espacio de búsqueda contiene muchos controles, algunos de ellos poco influyentes. No garantiza encontrar el mejor candidato posible, pero su presupuesto es explícito y fácil de ampliar.

Imaginemos 20 configuraciones igualmente probables e independientes, de las cuales tres pertenecen a una región prometedora. La probabilidad de no encontrar una configuración de esa región en un sorteo es \(17/20=0.85\). Con ocho extracciones independientes con reemplazo, la probabilidad de no visitarla nunca es:

\[P(\text{ningún éxito en 8 sorteos})=\left(\frac{17}{20}\right)^8\approx0.27249\]
\[P(\text{al menos un éxito})=1-0.85^8\approx0.72751\]

Por tanto, hay aproximadamente 72.75% de probabilidad de explorar esa región prometedora bajo los supuestos indicados. Esto no garantiza elegir un buen modelo: cada evaluación sigue necesitando CV confiable y la región prometedora es hipotética. Si extrajéramos configuraciones sin reemplazo de un conjunto finito, o con una distribución no uniforme, el cálculo cambiaría.

Para Logistic Regression suele ser razonable muestrear \(C\) en escala logarítmica (por ejemplo entre \(10^{-3}\) y \(10^2\)); muestrear de forma uniforme entre 0.001 y 100 concentraría casi todos los valores en la zona alta de C. Elegir distribuciones también exige conocimiento del modelo; no es un detalle técnico neutro.

19. Presupuesto de búsqueda, costo computacional y reproducibilidad

Para Grid Search con \(J\) candidatos y \(K\) folds, el número aproximado de ajustes es \(J K\), más el refit final si corresponde. Para Randomized Search con \(n_{iter}\) extracciones, será \(n_{iter}K\). Por ejemplo, seis candidatos de Random Forest y cuatro folds requieren \(6\times4=24\) ajustes; tres configuraciones de Logistic Regression requieren \(3\times4=12\). Un Random Forest contiene muchos árboles, por lo que un ajuste puede costar mucho más que uno de Logistic Regression.

\[\text{Costo de búsqueda}\approx\text{Candidatos}\times\text{Folds}\times\text{Costo por ajuste}\]

Grid Search cubre por completo la grilla discreta elegida, no la infinidad de configuraciones posibles. Randomized Search puede explorar espacios amplios con menor presupuesto, pero puede omitir combinaciones útiles. Otros procedimientos, como Bayesian Optimization y successive halving, usan resultados previos o recursos parciales para orientar búsquedas. Ninguno elimina la necesidad de Validation correcta.

Documenta la semilla de la división train/test, los folds, valores o distribuciones de Hyperparameters, métrica principal, versión del software y reglas de decisión. Utiliza semillas reproducibles cuando sea posible, pero no elijas una Random Seed afortunada después de mirar los scores. Al comparar una búsqueda amplia con otra pequeña, informa los presupuestos computacionales para no favorecer ocultamente al algoritmo que probó más alternativas.

20. Por qué CV ordinaria no audita por completo la selección

Debemos distinguir dos objetivos de evaluación. Pregunta A: «Para este candidato específico, \(C=10\), ¿cuál es su desempeño bajo cuatro folds?». CV estima ese desempeño para el candidato. Pregunta B: «Si uso un procedimiento que selecciona C entre diversas alternativas a partir de development, ¿cómo funcionará ese procedimiento completo con clientes realmente nuevos?». La segunda pregunta incluye variabilidad y posible optimismo generado por escoger el ganador.

GridSearchCV.best_score_ se calcula con folds que también se utilizaron para seleccionar el candidato. Reutilizar esa cifra como auditoría independiente de toda la búsqueda suele ser optimista. Un Test intacto permite una evaluación externa única del procedimiento elegido. Nested Cross-Validation proporciona evaluaciones externas repetidas sin involucrar el Test final en ninguna decisión.

Nested CV utiliza dos sistemas distintos de folds. Los inner folds eligen Hyperparameters utilizando exclusivamente el Training del outer fold. El outer validation fold evalúa todo ese procedimiento ajustado internamente y nunca se utiliza para elegir C durante esa iteración externa. Si permitimos que sus etiquetas influyan en la búsqueda interna, deja de ser una evaluación externa válida.

El cambio conceptual clave es que en Nested CV el «modelo» evaluado no es únicamente Logistic Regression: es el proceso completo preprocessing → search → selection → refit → predict. A continuación reproduciremos tres evaluaciones externas.

21. Nested CV: tres resultados completos de Outer Folds

Tomamos los mismos 288 clientes de development, sin abrir los 72 de Test. Utilizamos tres outer folds stratified: en cada iteración entrenamos con 192 clientes y evaluamos 96 clientes retenidos de development. Dentro de cada outer Training, otra CV de tres folds busca \(C\in\{0.1,1,10\}\). La búsqueda reajusta el C ganador con los 192 clientes de outer Training y predice una sola vez los 96 de outer Validation.

Outer fold C elegido en Inner Mejor Balanced Accuracy interna Balanced Accuracy externa
1 10 0.6391 0.5659
2 1 0.6089 0.5530
3 10 0.5724 0.6318

La media externa se calcula como:

\[\overline B_{outer}=\frac{0.565934+0.552958+0.631831}{3}\approx0.583574\]

Las puntuaciones internas ganadoras suelen ser superiores a las externas, y el Hyperparameter seleccionado cambia entre outer folds. Esa es precisamente la incertidumbre que el procedimiento ayuda a revelar. Los tres resultados no constituyen garantías y la diferencia entre \(0.6362\) (score CV de tuning ordinario) y \(0.5836\) (estimación Nested) no debe interpretarse como una corrección universal del sesgo: también influyen los tamaños de Training y los diseños de fold.

Para desplegar un modelo, después de esta evaluación podemos ejecutar la búsqueda final con todo development, reajustar el candidato elegido y consultar una sola vez el Test reservado. Nested CV evalúa el procedimiento de selección; no obliga a producir tres modelos operativos que deban promediarse.

Reconstruir un Outer Score a partir de las predicciones

En el Outer Fold 1, la búsqueda interna de tres folds eligió \(C=10\) utilizando únicamente los 192 registros de Outer Training. Después, el Pipeline reajustado clasificó los 96 registros reservados para Outer Validation. Los conteos fueron TN = 55, FP = 15, FN = 17, TP = 9. Son predicciones sobre el fold externo, no una Confusion Matrix de Training.

ClaseCorrectosTotalRecall
Churn (1)TP = 9TP + FN = 9 + 17 = 269/26 = 0.346154

Los 96 conteos concuerdan: \(55+15+17+9=96\). Acertar la mayoría de los casos sin Churn no compensa automáticamente la pérdida de muchos casos de Churn: Balanced Accuracy pondera por igual los dos Recall de clase. El mejor score interno, 0.639058, y el externo, 0.565934, responden preguntas distintas; no son dos mediciones del mismo estimador ajustado sobre las mismas observaciones.

El alcance de este Nested CV debe quedar preciso

Estos tres resultados evalúan una sola familia de algoritmos: un Pipeline de Logistic Regression cuyo hyperparameter \(C\) se selecciona mediante búsqueda interna. No evalúan independientemente el procedimiento más amplio que compara además Logistic Regression contra Random Forest. Para estimar ese selector de dos familias mediante Nested CV, cada partición de Outer Training debe ejecutar ambas búsquedas en los inner folds, seleccionar familia e hyperparameters sin consultar Outer Validation, reajustar el Pipeline seleccionado sobre Outer Training y evaluar Outer Validation una sola vez. Repetir para cada fold externo. El resultado 0.583574 no puede describirse como una estimación Nested del procedimiento conjunto de dos familias. El Test final reservado evalúa una sola vez el Pipeline efectivamente seleccionado, con la incertidumbre propia de su tamaño pequeño.

22. Incertidumbre: qué permiten concluir pequeñas diferencias

En el experimento grande, las medias de Balanced Accuracy fueron 0.6301 para \(C=1\) y 0.6362 para \(C=10\). La diferencia es aproximadamente 0.0061. Ambos presentan variación entre folds de varios puntos porcentuales. Por tanto, sería injustificado proclamar que \(C=10\) es categóricamente superior, aunque gane según nuestra regla preestablecida. El resultado de búsqueda representa una decisión bajo evidencia finita, no una demostración de que existe un único Hyperparameter correcto.

En Nested CV, los tres valores externos de Balanced Accuracy son 0.5659, 0.5530 y 0.6318. Su media es aproximadamente 0.5836. Una desviación estándar empírica describe variación entre estos folds, pero como comparten observaciones de Training, los intervalos construidos ingenuamente bajo independencia no son automáticamente válidos. Para afirmaciones más sólidas podrían necesitarse CV repetidas o agrupadas, métodos de remuestreo apropiados, pruebas estadísticas adaptadas al diseño y benchmarks independientes.

Para decisiones reales también importan otras preguntas: ¿es suficiente el Recall de Churn?, ¿cuánto cuesta cada contacto?, ¿empeora el desempeño para contratos Month-to-month?, ¿están calibradas las probabilidades?, ¿un modelo más sencillo se comportaría de manera similar? Son criterios legítimos si se estudian transparentemente, sin convertir Test en una fuente de tuning.

El mejor score CV significa **el mejor observado entre alternativas bajo este procedimiento**, no «mejor modelo del mundo» ni garantía de desempeño futuro.

Comparación de folds emparejados: ¿se mantiene la ventaja?

Como \(C=1\) y \(C=10\) se evaluaron en los mismos cuatro folds de Validation, debemos comparar sus scores por pares en vez de tratar los ocho scores como experimentos independientes. Restamos el valor de \(C=1\) al de \(C=10\) dentro de cada fold, con los valores redondeados de la Sección 16:

Los clientes de Validation son los mismos dentro de cada fold; diferencias calculadas con cuatro decimales

La ventaja promedio es 0.61 puntos porcentuales, no 0.61%. La desviación estándar muestral de estas cuatro diferencias emparejadas es:

\[s_d=\sqrt{\frac{(0-0.0061)^2+(0.0169-0.0061)^2+(-0.0094-0.0061)^2+(0.0169-0.0061)^2}{4-1}}\approx0.01305\]

Equivale aproximadamente a 1.31 puntos porcentuales de variación entre las diferencias observadas. La ventaja cambia de signo en Fold 3 y desaparece en Fold 1. Esto ayuda a reconocer inestabilidad, pero no constituye un Confidence Interval calibrado: los Training folds se superponen, los cuatro scores son dependientes y comparamos hyperparameters porque vimos los scores. Si preferimos un modelo más sencillo en caso de empate o exigimos una mejora mínima práctica, debemos fijar esa regla con datos de Development, nunca después de inspeccionar Test.

23. Test final: verificar la selección congelada una sola vez

Después de comparar ambas familias mediante CV en development, elegimos Logistic Regression con \(C=10\). Su Pipeline ya fue reajustado usando los 288 clientes de development, incluyendo imputación, Scaling, Encoding y estimación de coeficientes. Solo ahora predecimos los 72 clientes de Test. La Confusion Matrix observada tiene filas = resultado real y columnas = resultado predicho:

Real / Predicho Stay (0) Churn (1) Total fila
Realmente permanecen (0) TN = 48 FP = 5 53
Realmente cancelan (1) FN = 13 TP = 6 19
Total columna 61 11 72

Calculamos Sensitivity (Recall de Churn) \(=6/(6+13)=6/19\approx0.31579\). Specificity \(=48/(48+5)=48/53\approx0.90566\). El promedio es:

\[B_{Test}=\frac{6/19+48/53}{2}\approx0.610725\]
\[Accuracy_{Test}=\frac{48+6}{72}=0.7500\]

Las probabilidades producen ROC-AUC ≈ 0.7031 en esos mismos clientes de Test. ROC-AUC mide capacidad de ordenamiento a lo largo de Thresholds, mientras la Balanced Accuracy anterior utiliza el Threshold actual (0.50). No debemos confundirlas ni elegir un Threshold nuevo mirando las etiquetas de Test.

También informamos que el candidato seleccionado de Random Forest, evaluado solo para comparación después de congelar nuestra regla de selección de familias, produce Balanced Accuracy de Test ≈ 0.5204. Esa comparación posterior es descriptiva: no modifica el modelo ganador ni crea otro Test independiente. En un reporte operativo riguroso conviene destacar la decisión congelada y evitar nuevas rondas de decisiones basadas en Test.

La Balanced Accuracy de Test (0.6107) es menor que la media CV de development del modelo ganador (0.6362). Es una posibilidad normal de generalización; no justifica repetir la búsqueda a escondidas.

24. Cuándo StratifiedKFold es una elección incorrecta

Utilizamos StratifiedKFold porque los clientes sintéticos se generaron como observaciones independientes y porque la clase 1 es relativamente minoritaria. Stratification ayuda a conservar proporciones, pero no corrige dependencia entre observaciones. En telecomunicaciones reales puede haber registros del mismo hogar, cuenta empresarial o abonado en meses sucesivos.

Si el mismo abonado aparece en Training y Validation, un modelo puede parecer que generaliza cuando simplemente reconoce patrones de ese cliente. GroupKFold u otra división consciente de grupos mantiene juntos todos los registros de una persona u hogar. Para predicciones temporales debemos entrenar sobre el pasado y validar en períodos posteriores; los folds mezclados pueden permitir que información futura influya en pronósticos históricos. Usaríamos validación forward-time y, cuando corresponda, un gap por etiquetas tardías o ventanas móviles.

Pregunta de despliegue Principio de evaluación apropiado
Clientes nuevos independientes de distribución similar StratifiedKFold puede ser apropiado
Hogares u organizaciones completamente nuevos Holdout por grupos
Churn próximo trimestre con datos del año anterior Validación temporal hacia adelante
Observaciones mensuales repetidas de las mismas cuentas Respetar dependencias temporales y de entidad

Ningún Pipeline corrige un split design inválido. El orden es: definir momento y unidad de predicción, escoger folds, y ajustar preprocessing dentro de cada fold. RandomizedSearchCV y GridSearchCV heredan el diseño CV correcto o incorrecto que les proporcionemos.

25. Reproducir todo en Python: Pipeline, búsquedas y Nested CV

El siguiente laboratorio es completo y ejecutable con NumPy, pandas y scikit-learn. No es necesario descargar un CSV: los datos se generan mediante el código. Los generadores aleatorios fijos facilitan reproducir los resultados en entornos compatibles. Algunas diferencias pequeñas entre versiones de bibliotecas podrían surgir por cambios de Solver; la lógica del procedimiento sin Leakage es la misma.

Léelo en etapas: (1) generar los clientes y su Target sintético; (2) reservar Test antes de calcular estadísticas de preprocessing; (3) definir las ramas numérica y categórica; (4) ejecutar búsquedas Logistic y Random Forest únicamente sobre development; (5) utilizar un bucle externo para evaluar el procedimiento de tuning; y (6) evaluar la selección congelada sobre Test. El código también imprime los Fold Scores para que puedas compararlos con nuestras tablas.

import numpy as np,pandas as pd
from sklearn.model_selection import train_test_split,StratifiedKFold, GridSearchCV,cross_validate
from sklearn.compose import ColumnTransformer
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import OneHotEncoder,StandardScaler
from sklearn.impute import SimpleImputer
from sklearn.linear_model import LogisticRegression
from sklearn.ensemble import RandomForestClassifier
from sklearn.metrics import balanced_accuracy_score,roc_auc_score,confusion_matrix,accuracy_score
rng=np.random.default_rng(2205)
n=360
tenure=rng.integers(2,73,n)
tickets=rng.poisson(2.3,n)
drop=rng.normal(12,8,n).clip(0,40)
contract=rng.choice(['Month-to-month','One-year','Two-year'],n,p=[.50,.30,.20])
autopay=rng.choice(['Yes','No'],n,p=[.63,.37])
bill=rng.normal(74,17,n).clip(28,139)
logit=-2.35+.050*drop+.38*tickets-.021*tenure+np.where(contract=='Month-to-month',.85,np.where(contract=='One-year',.2,-.5))+np.where(autopay=='No',.32,0)+.009*(bill-75)
prob=1/(1+np.exp(-logit))
y=rng.binomial(1,prob)
X=pd.DataFrame({'tenure_months':tenure,'support_tickets':tickets,'usage_drop_pct':drop,'contract':contract,'autopay':autopay,'monthly_bill_usd':bill})
# introduce missingness only for training-compatible handling
X.loc[rng.choice(n,18,replace=False),'usage_drop_pct']=np.nan
X_dev,X_test,y_dev,y_test=train_test_split(X,y,test_size=.20,random_state=22,stratify=y)
num=['tenure_months','support_tickets','usage_drop_pct','monthly_bill_usd'];cat=['contract','autopay']
prep=ColumnTransformer([('num',Pipeline([('imputer',SimpleImputer(strategy='median')),('scaler',StandardScaler())]),num),('cat',OneHotEncoder(handle_unknown='ignore'),cat)])
pipe=Pipeline([('prep',prep),('model',LogisticRegression(max_iter=2000,random_state=22))])
params={'model__C':[.1,1,10]}
cv=StratifiedKFold(n_splits=4,shuffle=True,random_state=22)
search=GridSearchCV(pipe,params,scoring='balanced_accuracy',cv=cv,refit=True,return_train_score=True,n_jobs=1)
search.fit(X_dev,y_dev)
print('samples',len(X_dev),len(X_test),'churn rates',np.mean(y_dev),np.mean(y_test))
print('class count',np.unique(y_dev,return_counts=True),np.unique(y_test,return_counts=True))
print('scores')
for i,p in enumerate(search.cv_results_['params']):
 print(p, [round(search.cv_results_[f'split{j}_test_score'][i],4) for j in range(4)],round(search.cv_results_['mean_test_score'][i],6), round(search.cv_results_['std_test_score'][i],6))
print('best',search.best_params_,search.best_score_)
y_pred=search.predict(X_test)
print('test score',balanced_accuracy_score(y_test,y_pred), 'accuracy',accuracy_score(y_test,y_pred),'roc auc',roc_auc_score(y_test,search.predict_proba(X_test)[:,1]),'conf',confusion_matrix(y_test,y_pred))
# compare rf with small grid
forest=Pipeline([('prep',prep),('model',RandomForestClassifier(random_state=22,n_estimators=150))]);rfsearch=GridSearchCV(forest,{'model__max_depth':[3,7,None],'model__min_samples_leaf':[2,8]},cv=cv,scoring='balanced_accuracy',n_jobs=1)
rfsearch.fit(X_dev,y_dev)
print('RF best',rfsearch.best_params_,rfsearch.best_score_)
print('RF test',balanced_accuracy_score(y_test,rfsearch.predict(X_test)))
# nested CV compare only log reg for runtime
outer=StratifiedKFold(n_splits=3,shuffle=True,random_state=71)
inner=StratifiedKFold(n_splits=3,shuffle=True,random_state=72)
for f,(tr,va) in enumerate(outer.split(X_dev,y_dev),1):
 s=GridSearchCV(pipe,params,cv=inner,scoring='balanced_accuracy',refit=True)
 s.fit(X_dev.iloc[tr],y_dev[tr]); pred=s.predict(X_dev.iloc[va]); print('outer',f,'train',len(tr),'validation',len(va),'best',s.best_params_['model__C'],'inner best score',round(s.best_score_,6),'outer',round(balanced_accuracy_score(y_dev[va],pred),6),'conf',confusion_matrix(y_dev[va],pred).tolist())

Qué hace GridSearchCV internamente

Para cada candidato \(C\), clona el Pipeline completo cuatro veces. Cada clon aprende imputaciones, escalas, categorías y coeficientes Logistic exclusivamente desde el Training de ese fold. Después evalúa Validation, promedia los cuatro resultados y selecciona el candidato con mayor media. Como refit=True, se ajusta un Pipeline final nuevo usando todo development. Ese es el objeto que se utiliza para predict(X_test).

Alternativa: RandomizedSearchCV

Este ejemplo es ejecutable después del laboratorio completo anterior. La distribución Log-Uniform permite explorar valores de C pequeños y grandes a lo largo de varios órdenes de magnitud:

from scipy.stats import loguniform
from sklearn.model_selection import RandomizedSearchCV
random_search = RandomizedSearchCV(
    estimator=pipe,
    param_distributions={'model__C': loguniform(1e-3, 1e2)},
    n_iter=8,
    cv=cv,
    scoring='balanced_accuracy',
    random_state=22,
    refit=True,
    n_jobs=1,
)
random_search.fit(X_dev, y_dev)
print(random_search.best_params_, random_search.best_score_)

Conserva el Pipeline como estimador y deja Test intacto. Random Search tiene un presupuesto acotado; su nombre no evita por sí solo Leakage ni optimismo de selección.

26. Auditar un procedimiento incorrecto y corregirlo completamente

Considera esta secuencia incorrecta: mezclar development y Test; ajustar imputación y Scaling sobre todas las filas; ejecutar Grid Search; inspeccionar scores de Test para distintas grillas; quedarse con la configuración de mejor Test; publicar ese número como evidencia independiente. Hay tres fallas distintas: el preprocessing aprendió de Features de evaluación futura; Test influyó en la selección; y la cifra publicada fue optimizada sobre la misma muestra que se presenta como independiente.

El protocolo corregido es:

  1. Definir pregunta predictiva, unidad, momento y métrica principal antes de modelar.
  2. Reservar Test y registrar exactamente qué IDs contiene.
  3. Escoger folds apropiados para clases, grupos o tiempo. Ubicar todo preprocessing aprendido dentro del Pipeline.
  4. Utilizar CV para seleccionar candidatos sin mirar Test. Si queremos estimar el procedimiento completo, usar Nested CV o un conjunto de auditoría externo.
  5. Reajustar el Pipeline elegido con todos los registros permitidos de development.
  6. Evaluar Test una sola vez. Registrar errores y limitaciones. No reajustar el modelo usando esos resultados y seguir llamando intacto al mismo Test.

Una falla sutil consiste en construir una nueva grilla después de observar un Test decepcionante. En ese momento Test ha pasado a formar parte de development. Para afirmar que tenemos una nueva evaluación independiente necesitamos datos nuevos, verdaderamente no consultados, no simplemente otra Random Seed sobre el mismo Test. Las modificaciones originadas por monitoreo de producción también requieren evaluaciones temporales cuidadosas.

Una separación limpia no basta por sí sola. Toda decisión informada por etiquetas retenidas —elección de Threshold, de Features o rediseño de una grilla tras analizar errores— cuenta como parte del desarrollo.

27. Errores frecuentes: diagnosticar el mecanismo, no solo el síntoma

1. Reportar Training como generalización. Sus etiquetas participaron en el ajuste. Corrección: evaluar mediante folds y Test independiente.

2. Llamar “Validation” a Test. Si se utiliza repetidamente para tuning, ya es development. Corrección: reservar otra muestra futura para una auditoría realmente independiente.

3. Ajustar StandardScaler antes de crear los folds. Las Features de Validation influyen en medias y escalas. Corrección: colocar el Scaler dentro del Pipeline CV.

4. Hacer One-Hot Encoding por separado en las particiones. Las columnas pueden desalinearse. Corrección: ajustar OneHotEncoder en Training y transformar las observaciones retenidas con las categorías almacenadas.

5. Cambiar la métrica después de mirar los scores. El ganador se beneficia también de esa selección. Corrección: fijar métricas principales y diagnósticos secundarios previamente.

6. Tratar folds como experimentos independientes. Los conjuntos Training se superponen. Corrección: interpretar la dispersión descriptivamente y usar un diseño válido para incertidumbre.

7. Confundir Grid Search con optimización universal. El ganador es el mejor entre los candidatos probados. Corrección: declarar grilla y presupuesto.

8. Creer que Random Search siempre gana. Puede ignorar regiones útiles. Corrección: estudiar distribuciones y presupuesto, y validar justamente.

9. Seleccionar la Random Seed más afortunada. Se convierte en otro parámetro optimizado. Corrección: fijarla previamente o usar un diseño de evaluación repetida apropiado.

10. Reajustar usando Test antes de evaluarlo. Destruye el holdout independiente. Corrección: hacer refit solo con development.

11. Ajustar Thresholds sobre Test. Aunque los coeficientes sean fijos, elegir Threshold con sus etiquetas constituye selección. Corrección: elegirlo dentro de development.

12. Usar CV mezclada para pronósticos temporales. Datos futuros pueden contaminar el entrenamiento histórico. Corrección: validación temporal hacia adelante.

13. Distribuir registros de una misma cuenta entre folds. Puede filtrarse la identidad del cliente. Corrección: GroupKFold u otro diseño por entidad.

14. Interpretar best_score_ como auditoría externa. Sirvió para elegir el candidato. Corrección: Nested CV o Test reservado.

15. Declarar universalmente superior al algoritmo con mayor media CV. Importan variabilidad y presupuesto de búsqueda. Corrección: contextualizar por datos, métrica, grilla e incertidumbre.

16. Ignorar costos de despliegue. Balanced Accuracy por sí sola no mide rentabilidad de retención. Corrección: incorporar restricciones y un modelo de costos defendible en validaciones futuras.

28. Práctica y transferencia: 20 preguntas resueltas

Los ejercicios avanzan desde la reproducción numérica hacia la auditoría de decisiones. Intenta resolver cada uno antes de desplegar su solución. No buscamos repetir definiciones, sino demostrar que puedes seguir los datos a lo largo de la selección e identificar cuándo una evaluación deja de ser independiente.

1. Calcula Accuracy con 12 predicciones correctas de 15.

Accuracy es 12/15 = 0.80. El numerador incluye todos los aciertos y el denominador todas las observaciones retenidas. No describe el desempeño por clase.

2. ¿Por qué no puede usarse como vecino la etiqueta de un cliente retenido?

La etiqueta es justamente el resultado que queremos predecir. Incluirla en el ajuste permite que su propia respuesta influya en la predicción, invalidando la evaluación.

3. Calcula la Accuracy media para k=1.

Los resultados son 3/5=0.60, 3/5=0.60 y 2/5=0.40. Media = (0.60+0.60+0.40)/3 = 0.5333. k=1 resulta inferior a k=7 según este protocolo.

4. ¿Por qué gana k=7 con votación uniforme?

Los tres folds producen 0.80, 0.80 y 0.80: media 0.80, superior a la de las otras nueve configuraciones. Es un ganador dentro de una grilla finita, no un óptimo universal.

5. Cuenta los ajustes para cinco k, dos reglas de votación y tres folds.

Hay 5×2=10 configuraciones y 10×3=30 ajustes en folds. Si después se reajusta el ganador con todo development, agregamos un ajuste final: 31 en total.

6. Interpreta la Confusion Matrix del Test pequeño para k=7.

Predicciones 0,0,1,1,1 y etiquetas reales 0,0,0,1,1. Entonces TN=2, FP=1, FN=0, TP=2; Accuracy=(2+2)/5=0.80. Un error adicional reduciría Accuracy en 20 puntos porcentuales.

7. Un fold aprende media 20 y desviación 8.165. Estandariza un valor 100 de Validation.

Utiliza las estadísticas congeladas de Training: z=(100−20)/8.165≈9.798. No recalcules media ni escala en Validation: cambiarías la referencia y producirías Leakage.

8. ¿Por qué preferimos C=10 frente a C=1 y qué NO podemos concluir?

Las medias CV son 0.6362 y 0.6301; C=10 gana según la regla predefinida por aproximadamente 0.0061. Esa diferencia no demuestra superioridad universal ni necesariamente una mejora relevante para futuros clientes.

9. Explica por qué C y un coeficiente Logistic son cantidades distintas.

C lo fija el procedimiento de selección y controla Regularization inversa. El coeficiente se aprende al minimizar la Loss penalizada usando Training de cada fold. Cambiar C puede modificar los coeficientes aprendidos.

10. Calcula 1−(17/20)^8 y explica sus supuestos.

El resultado es aproximadamente 0.72751, o 72.75%. Supone ocho extracciones independientes con reemplazo, cada una con probabilidad 3/20 de entrar en la región prometedora hipotética. No garantiza calidad del modelo.

11. ¿Qué es optimismo de selección si 20 modelos tienen desempeño verdadero idéntico?

El máximo de 20 scores de Validation ruidosos tiende a superar el valor verdadero compartido, incluso si cada score individual es insesgado. El ganador suele beneficiarse parcialmente del ruido favorable.

12. Indica qué decisiones no puede influir el Outer Validation.

No debe seleccionar Hyperparameters, ajustar Scalers/Imputers, elegir Features, rediseñar la grilla ni ajustar Thresholds dentro de esa iteración. Su función es evaluar el procedimiento ya optimizado internamente.

13. Calcula la media externa de 0.565934, 0.552958 y 0.631831.

Suma = 1.750723; al dividir entre 3 obtenemos 0.583574 (redondeado). Resume tres evaluaciones externas, no una probabilidad certificada de acierto para cada cliente futuro.

14. Calcula Balanced Accuracy de Test con TN=48, FP=5, FN=13 y TP=6.

Recall de Churn=6/(6+13)=6/19≈0.31579. Specificity=48/(48+5)=48/53≈0.90566. Promedio=(0.31579+0.90566)/2≈0.610725.

15. ¿75% Accuracy en Test significa detección aceptable de Churn?

No necesariamente. Aunque acertamos 54/72 etiquetas, solo detectamos 6/19 cancelaciones (Recall ≈31.6%). Su aceptabilidad depende de costos de omisión, recursos y objetivos operativos fijados previamente.

16. Elige una evaluación para un cliente observado cada mes.

No distribuyas aleatoriamente meses de la misma persona entre folds. Usa separación temporal y por entidad compatible con pronosticar meses posteriores; mantén preprocessing y etiquetas válidos temporalmente.

17. Un colega prueba otra grilla después de un Test decepcionante. ¿Puede seguir llamándolo auditoría independiente?

No. Los resultados de Test influyeron en development, por lo que la muestra reutilizada participa en selección. Congela el procedimiento y consigue datos realmente nuevos para una auditoría externa.

19. Calcula la ventaja emparejada de C = 10 sobre C = 1 e interpreta su magnitud.

Usa los cuatro folds idénticos de Validation de la Sección 16. Sus diferencias (C = 10 menos C = 1) son 0, +0.0169, −0.0094, +0.0169; el promedio es \((0+0.0169-0.0094+0.0169)/4=0.0061\), o 0.61 puntos porcentuales. La desviación estándar muestral de las diferencias es aproximadamente 0.01305 (1.31 puntos porcentuales). Como Fold 3 favorece C = 1 y los folds comparten registros de Training, esa pequeña diferencia promedio no demuestra que C = 10 sea mejor para clientes futuros. La regla de búsqueda prefijada sigue escogiendo C = 10; una nueva inferencia exige evidencia adecuadamente independiente.

20. La empresa también elige entre Logistic Regression y Random Forest. ¿Qué debe quedar dentro de Nested CV?

En cada uno de los tres outer folds, reserva 96 clientes para Outer Validation y utiliza los otros 192 para el tuning interno. Sobre esos 192, utiliza los mismos tres inner folds apropiados para buscar los tres valores de Logistic C y las seis configuraciones de Random Forest mediante Balanced Accuracy. Por tanto, hay \(3(3+6)=27\) ajustes internos de candidato-fold por ronda externa, o \(3\times27=81\) en las tres rondas externas, sin contar los reajustes finales. Compara los mejores scores internos de ambas familias, selecciona una familia y sus parámetros, reajusta solo la ganadora sobre los 192 registros y evalúa los 96 casos externos. No uses esas 96 etiquetas para escoger la familia. El Nested CV existente, con media 0.583574, evalúa solo la selección de Logistic C; no puede presentarse como un resultado verificado del selector conjunto de familias.

A la inversa, una buena explicación conceptual sin cálculos reproducibles de folds tampoco demuestra dominio suficiente. Ambas competencias son necesarias.

29. Síntesis, glosario y futuro laboratorio reproducible

Síntesis. Empezamos con 15 clientes y verificamos candidatos k-NN reteniendo observaciones. Después pasamos a 360 clientes sintéticos y comparamos clasificadores con las mismas particiones de development. Grid Search seleccionó Logistic Regression con \(C=10\); Nested CV ofreció una evaluación más exigente del procedimiento de selección; y Test, completamente intacto, produjo Balanced Accuracy ≈ 0.6107, inferior a la media CV ganadora. No son contradicciones: estiman cantidades diferentes con información distinta.

Glosario. Parameter: cantidad aprendida, como un coeficiente. Hyperparameter: control externo como k, C o profundidad. Cross-Validation: evaluación interna mediante subconjuntos retenidos. Grid Search: evaluación de una grilla definida. Randomized Search: extracción aleatoria de distribuciones de parámetros. Stratification: conservación aproximada de proporciones de clases. Refit: ajuste final de la configuración ganadora sobre development permitido. Nested CV: selección interna y evaluación externa. Data Leakage: información de evaluación influye indebidamente en ajuste o selección. Selection Bias: optimismo originado por elegir el mejor entre scores ruidosos. Balanced Accuracy: media de Sensitivity y Specificity en clasificación binaria.
