Loan Default Predictor

Credit risk modeling with the Home Credit dataset: from business understanding and exploratory data analysis to XGBoost, SHAP explanations and deployment in Streamlit.

Educational Project

Project question

Can we estimate the probability that a loan applicant will default? This project builds an end-to-end machine learning pipeline that takes applicant information and predicts credit risk in a didactic, student-friendly way.

Main idea: the output is not merely “approve” or “deny.” The most informative output is a default probability. That probability can then be converted into a lending decision using a threshold chosen by the institution.

Why this project matters

Credit risk modeling is one of the classic applications of data science in finance. Banks and lenders must decide which applicants are likely to repay and which ones are more likely to default. If the institution approves too many risky loans, losses rise. If it denies too many good borrowers, revenue is lost and good customers are pushed away.

Economic intuition: a single large default can erase the profits from many good loans. That is why classification, probability estimation and interpretability matter so much in credit scoring.

Dataset, source and prediction target

This project uses the Home Credit Default Risk dataset from the 2018 Kaggle competition hosted by Home Credit Group. The competition asks participants to estimate applicants' repayment ability and evaluates submitted probabilities using the Area Under the Receiver Operating Characteristic Curve (ROC AUC).

Official source: Home Credit Default Risk — Kaggle ↗. The competition data are subject to Kaggle's competition rules; this portfolio therefore links to the official source rather than redistributing the raw competition CSV files.

Which files are used in this project?

The original competition contains several related tables. This educational implementation focuses primarily on application_train.csv, the labeled application-level table. The companion application_test.csv has a similar application structure but does not expose TARGET, because it was created for competition scoring. The historical tables are valuable extensions, but they are not required for the core modeling pipeline presented here.

The application data include financial, demographic and application-related variables such as AMT_INCOME_TOTAL, AMT_CREDIT, AMT_ANNUITY, DAYS_BIRTH, DAYS_EMPLOYED and the anonymized external-source variables EXT_SOURCE_1, EXT_SOURCE_2 and EXT_SOURCE_3.

Important precision: the EXT_SOURCE_* variables are anonymized external-source scores. We should not label them as conventional credit-bureau scores or assign them a more specific origin than the competition documentation supports.

A machine-learning view of the problem

Suppose applicant i is represented by p observed predictor variables. We collect those measurements into a feature vector:

\[ \mathbf{x}_i = \begin{bmatrix} x_{i1} & x_{i2} & \cdots & x_{ip} \end{bmatrix}^{\mathsf T} \]Each \(x_{ij}\) is one measured characteristic of applicant \(i\), such as income, requested credit, annuity, age, employment history or an external-source score.

The response variable is binary:

\[ Y_i \in \{0,1\} \]Here \(Y_i=1\) is the competition's positive payment-difficulty class and \(Y_i=0\) is the negative class.

The statistical learning problem is to estimate the conditional probability

\[ \widehat{p}(\mathbf{x}) = \widehat{P}\!\left(Y=1\mid \mathbf{X}=\mathbf{x}\right) \]Interpretation: given an applicant with observed characteristics \(\mathbf{x}\), what probability does the fitted model assign to the positive class?

A probability is not yet a class decision. To obtain a binary prediction, we introduce a classification threshold \(t\):

\[ \widehat{Y} = \begin{cases} 1, & \widehat{p}(\mathbf{x}) \ge t,\\[4pt] 0, & \widehat{p}(\mathbf{x}) < t. \end{cases} \]The commonly used \(t=0.50\) is only a convention. Lowering or raising the threshold changes the tradeoff between detecting more positive cases and generating more false alarms.
Example: if \(\widehat{p}(\mathbf{x})=0.29\), then a threshold of \(0.50\) produces \(\widehat{Y}=0\), while a threshold of \(0.25\) produces \(\widehat{Y}=1\). The model probability did not change; only the decision rule changed.

This project is structured as a step-by-step learning sequence. The notebooks move from understanding the raw data, to cleaning and feature engineering, to training models, evaluating them and finally exporting the artifacts for deployment in a Streamlit app.

Stage 1 — Setup & Data

Load the dataset, inspect dimensions, understand the target and establish the train/test workflow. This stage answers a foundational question: what exactly are we predicting and why?

Stage 2 — Exploratory Data Analysis (EDA)

Study the distribution of the target and the predictor variables. This is where we begin to ask whether income, annuity, age or external scores appear related to default risk.

Stage 3 — Preprocessing & Feature Engineering

Handle missing values, encode categorical features, scale numerical variables and create engineered ratios such as credit-to-income and annuity-to-income.

Stage 4 — Models & Evaluation

Train three models—Logistic Regression, Random Forest and XGBoost—then compare them using metrics that make sense for an imbalanced credit-risk problem.

Stage 5 — SHAP & Export

Explain predictions using SHAP and export the model artifacts so the final pipeline can be used inside the Streamlit application.

Why class imbalance matters

Only about 8.1% of loans are defaults, while about 91.9% are non-defaults. This is called class imbalance.

Important warning: if a model predicts “no default” for every applicant, it would still be about 91.9% accurate. That sounds good, but the model would completely fail at the business objective because it would miss every risky borrower.

That is why this project does not rely on accuracy alone. It also uses SMOTE, class-aware metrics and probability-based evaluation.

\[\mathrm{Accuracy}=\frac{TP+TN}{TP+TN+FP+FN}\]Accuracy is easy to compute but can be misleading when one class dominates.
\[\mathrm{Recall}=\frac{TP}{TP+FN}\]Recall matters greatly in credit risk because a false negative means approving an applicant who later defaults.

SMOTE and resampling

SMOTE stands for Synthetic Minority Oversampling Technique. Instead of merely duplicating default cases, it creates synthetic minority examples by interpolating between existing default observations.

Small example: if one defaulting borrower has income = 30k and another has income = 35k, SMOTE can create a synthetic borrower with income around 32k or 33k, together with correspondingly interpolated values for other features. This helps the model “see” the default region more clearly during training.

The three models in the project

1) Logistic Regression

This is the baseline classification model. It computes a linear score and pushes it through a sigmoid function:

\[z=\beta_0+\beta_1x_1+\beta_2x_2+\cdots+\beta_px_p\]\[\widehat{p}(\mathbf{x})=\frac{1}{1+e^{-z}}\]The sigmoid function converts any real-valued score into a number between 0 and 1, which we interpret as a default probability.

Why it is useful: it is simple, fast and interpretable. If it performs well, it provides a strong benchmark.

2) Random Forest

A Random Forest combines many decision trees. Each tree sees a bootstrap sample of the data and a random subset of features. The final probability is based on the ensemble of trees.

\[\widehat{p}_{RF}(\mathbf{x})=\frac{1}{B}\sum_{b=1}^{B}\widehat{p}_b(\mathbf{x})\]Here Tb(x) is the prediction from tree b, and B is the number of trees.

Why it helps: it captures nonlinear patterns and interactions that Logistic Regression might miss.

3) XGBoost

XGBoost is the strongest model in the project. It builds trees sequentially, where each new tree tries to correct the errors of the previous ensemble.

\[F_M(\mathbf{x})=F_0(\mathbf{x})+\sum_{m=1}^{M}\eta f_m(\mathbf{x})\]In words: the final score is the sum of many weighted weak learners. This boosting strategy often performs very well on structured tabular data.

In the project documentation, the XGBoost model achieved an AUC of about 0.76, which is a strong result for a difficult real-world problem.

Evaluation metrics and interpretation

Because this is a credit-risk classification task, we use multiple metrics rather than a single number.

Precision

\[\mathrm{Precision}=\frac{TP}{TP+FP}\]

Of the applicants predicted to default, how many actually default?

Recall

\[\mathrm{Recall}=\frac{TP}{TP+FN}\]

Of the true defaulters, how many did the model catch?

F1 Score

\[F_1=2\frac{\mathrm{Precision}\cdot\mathrm{Recall}}{\mathrm{Precision}+\mathrm{Recall}}\]

Balances precision and recall in one summary measure.

AUC-ROC

\[\mathrm{AUC}=P\!\left(s(\mathbf{X}^{+})>s(\mathbf{X}^{-})\right)\]

Interpretation: if we randomly choose one defaulting and one non-defaulting borrower, how often does the model rank the defaulter higher?

Business interpretation: a false negative is often the most expensive error in lending, because it means the bank approved a risky borrower. That is why recall and AUC are especially important.

Worked probability example

Suppose the model evaluates a borrower and returns

\[\widehat{p}(\mathbf{x})=0.29\]

This means the estimated default probability is 29%. If the lender uses a threshold t = 0.50, the applicant would not be automatically flagged as default. But if the lender uses a more conservative threshold t = 0.25, the same applicant would be flagged as risky.

Lesson: the model output and the business decision are related but not identical. The threshold encodes the institution’s risk appetite.

Preprocessing, scaling and feature engineering

The project applies standard supervised-learning hygiene:

  • Train/test split with stratification so class proportions remain similar in both sets.
  • One-hot encoding for categorical variables.
  • StandardScaler for numerical variables when appropriate.
  • Engineered features such as CREDIT_INCOME_RATIO = AMT_CREDIT / AMT_INCOME_TOTAL and ANNUITY_INCOME_RATIO = AMT_ANNUITY / AMT_INCOME_TOTAL.
\[z_i=\frac{x_i-\mu_{\mathrm{train}}}{\sigma_{\mathrm{train}}}\]This is the standardization formula. It centers a numerical variable by subtracting its mean and rescales it by dividing by its standard deviation.
Data leakage warning: the scaler must be fit on the training set only. If information from the test set is used while preprocessing, the evaluation becomes too optimistic.

Model explainability with SHAP

Regulated financial applications need more than raw predictive performance. They also need explanations. This project uses SHAP (SHapley Additive exPlanations) to explain both global and individual predictions.

\[f(\mathbf{x})=\phi_0+\sum_{j=1}^{p}\phi_j\]The baseline prediction is \phi0. Each feature contribution \phij pushes the final prediction up or down.

For example, a low external score may push the risk upward, while a stable income or lower annuity burden may push the risk downward.

Why students should care: SHAP is the bridge between predictive accuracy and interpretability. It helps us answer the question, “Why did the model produce this prediction?”

Deployment: from notebook to web application

The project is not limited to notebooks. It also includes a Streamlit application that loads the final model, scaler and feature names, accepts user input and returns a predicted default probability together with a risk category.

Risk categories used in the app: prob < 0.20 → LOW 0.20 ≤ prob < 0.50 → MEDIUM prob ≥ 0.50 → HIGH

This is an excellent portfolio feature because it shows not only model training but also packaging and communication of results to an end user.

Two deeper lessons: calibration and interpretation

Discrimination is not calibration. ROC AUC tells us how well the model ranks positive cases above negative cases across thresholds. It does not tell us whether a predicted probability of 20% actually corresponds to an event rate near 20%. A production-oriented extension should therefore study calibration curves and metrics such as the Brier score.

\[ \mathrm{Brier\ Score}=\frac{1}{n}\sum_{i=1}^{n}(\widehat{p}_i-y_i)^2 \]Lower values indicate that predicted probabilities are, on average, closer to the observed binary outcomes.

Explainability is not causality. SHAP describes how the fitted model uses features to produce a prediction. A large SHAP contribution does not prove that changing that variable would causally change the applicant's true repayment behavior.

Educational-use limitation: this project is a portfolio and learning exercise, not a production underwriting system. Real credit decisioning requires substantially more validation, governance, fairness analysis, legal/compliance review, monitoring and institution-specific controls.

Final takeaway

This is a strong educational project because it combines finance, machine learning, model evaluation, interpretability and deployment. It teaches not just how to fit a classifier, but how to think through the entire lifecycle of a practical data science system.
